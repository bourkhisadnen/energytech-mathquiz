# The app icon — and the dead service worker it uncovered

**Date:** 2026-09-11. Build `v57-app-icon` (was `v56-ch04-source-typos`).
Front-end only — `Code.gs` untouched, so no Apps Script redeploy.

Adnen sent a finished icon (a blue rounded square: white worksheet, pencil,
green tick) and asked for it to be used as the app's icon/logo. Two thirds of
the work turned out to be something else.

## The service worker had not parsed for weeks

While adding the icons to `service-worker.js`'s precache list I noticed a line
with no trailing comma:

```js
  './images/ch03_q68_screw.jpg'      // <- no comma
  // Chapter 12A's drawings. ...
  './figures_ch12a/0132f9050e1a.svg',
```

Two adjacent string literals. `node --check` confirms it: **SyntaxError**. So
the worker never parsed, `register()` rejected, and `app.js` swallowed the
rejection:

```js
navigator.serviceWorker.register('./service-worker.js').catch(() => {});
```

**The app therefore had no offline support and no precaching at all.** Not
degraded — absent.

**I introduced it**, appending Chapter 12A's 162 figure paths and dropping the
comma on the line above the new block. Confirmed by checking the older
delivered packages: `energytech_quiz_app_chapter03.zip`,
`..._intakes.zip` and `..._with_accounts.zip` all parse; it broke at v51 and
shipped in every build since (v51 → v56).

### Why nothing caught it

Every existing suite drives the page over a live http-server, and **an app with
a dead service worker is indistinguishable from a working one when the network
is up.** The suites test the app; nothing tested the app *shell*. The swallowed
rejection removed the last visible symptom.

This is the same shape as the mutation-testing lesson from Chapter 12A: *the
test observed an outcome that the code under test was not the only possible
cause of.* Here it is worse — nothing observed the outcome at all.

## `test_appshell.js` — 30 checks

New suite, deliberately end-to-end rather than textual:

- `service-worker.js` parses (`node --check`, kept because it names the line —
  `register()` rejecting does not)
- every path in the precache list exists on disk. `cache.addAll()` is atomic,
  so **one 404 fails the whole install** and leaves trainees with nothing
  cached, silently
- the worker really registers, reaches `activated`, and the cache ends up
  holding all 239 files
- the cache name carries a version, so a new build supersedes the old one
- the manifest's icons exist and really are the size they claim (read from the
  PNG's IHDR header, not trusted)
- both full-bleed icons are genuinely opaque and the plain ones genuinely are
  not — read pixel by pixel off a canvas
- the header logo renders, at a sane size, with empty `alt`

**Verified to bite**, both ways: putting the comma back fails the parse check
*and* the registration check; the run drops to 24/27.

Also added to `mutate_backend.js`, which now patches a **fourth** file
(`service-worker.js`, alongside `Code.gs`, `app.js`, `worksheet_tex.js`) with
two mutants: the missing comma, and a precache entry pointing at a file that
does not exist.

## The icon set: one source, six files

Generated by `tools/make_icons.py` from `tools/icon-source.png`. The platforms
disagree about what an icon is, so these are not resizes of each other:

| file | why it exists |
|---|---|
| `icon-192.png`, `icon-512.png` | manifest `purpose: any`; artwork as drawn, transparent corners kept |
| `icon-maskable-512.png` | Android crops adaptive icons to a circle, which would cut the pencil and the document's corners off. Artwork scaled into the middle 80% on a full-bleed field of **its own** blue, so the rounded-square edge vanishes into the field instead of showing as a seam |
| `apple-touch-icon.png` | iOS ignores the manifest, ignores transparency, and paints unset pixels **black**. Deliberately opaque; iOS applies its own rounded mask |
| `favicon-32.png`, `favicon-16.png` | 16px is what a tab actually draws; letting the browser downscale the 32 blurs it |

The old `icon.svg` — a placeholder of blue lines and dots, in a different blue,
that nothing had ever replaced — is deleted, with its three references
(`index.html`, the manifest, the precache list) repointed.

### Four things the source image needed

Each was found by measuring rather than by eye, and each is handled in the
generator so a future icon gets the same treatment:

1. **A ~5% transparent margin.** Trimmed to the artwork's bounding box so the
   rounded square fills the canvas, the way an app icon is normally drawn. The
   bbox is 1121×1135 — not quite square — so it is centred on a square canvas
   rather than stretched.
2. **The field blue is not the commonest colour.** Sampling the mode returns
   the *white* of the document sheet, which covers more of the icon than the
   background does. Taking it from a ring just inside the edge gives `#125AE5`.
   The first attempt used a stray fully-opaque pixel's `#175EED` and left a
   visible seam in the maskable icon.
3. **The whole image is ~1% translucent** — alpha 253/254, not 255, across
   229k of 262k pixels. An export artifact. It also wrecks PNG compression:
   the alpha channel carried more entropy than the artwork.
4. **The "flat" colours are dithered** — 9,629 distinct colours in a six-colour
   design.

With those cleaned and the files written as palette PNGs (PNG8 + tRNS, 8 bits
per pixel instead of 32), the set went from **426 KB to 31 KB** — which matters
because the service worker now genuinely precaches all of it onto every
trainee's device. Mean error 1.5/255, invisible at any size the icon is drawn.

### A bug worth remembering: `paste` blends alpha too

Both full-bleed icons came out **not opaque** — minimum alpha 191 at the
artwork's antialiased edge. `Image.paste(art, pos, art)` blends the source's
alpha into the destination as well as its colour, so pasting artwork with
transparent edges onto an opaque field pulls the field's alpha down with it.
`Image.alpha_composite` is the correct call. Caught by asserting min-alpha per
file rather than by looking, then fixed in one shared helper — the maskable was
fixed first and the Apple icon still had it, which is exactly why it is one
helper now.

## Also in the app

The icon sits in the page header beside the title (`.header-brand` /
`.app-logo`), with `alt=""` since the `h1` next to it already names the app. It
gets a drop shadow because the icon's blue is lighter than the header's navy
gradient and looked pasted-on flat without one. On screens under 640px the
title wraps to four lines, so the logo aligns to the top there rather than
floating against the gap between title and subtitle.

`theme_color` was **left alone** at `#006fae`. It tints the browser chrome and
should track the app's own header, not the icon; the icon's `#125AE5` would
clash with the `#002673 → #0078b8` gradient. (Worth noting separately that
`#006fae` already matches neither — the CSS uses `#0078b8`. Pre-existing, not
touched.)
